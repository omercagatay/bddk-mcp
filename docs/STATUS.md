## What is ready at repository level

- Packaged stdio and Streamable HTTP MCP entry points with a strict public tool contract.
- Explicit corpus preparation: `bddk-mcp build`, `bddk-mcp sync`, `bddk-mcp export` (refuses a corpus file that is not ready and then writes nothing to `seed_data/`), and the read-only `bddk-mcp info`; the serving process never writes the corpus. A plain `sync` re-indexes a stored document that lacks current chunks from its stored text instead of downloading it again.
- Fail-closed remote HTTP configuration (exact Host/Origin allowlists, JWT or explicit unauthenticated opt-in).
- Container image that carries the built corpus file, and a single-service Compose topology for local development; Railway remains a development/preview profile.
- Automated coverage across runtime, corpus build and readiness, retrieval, extraction quality and the HTTP transport.

## Upgrading an existing corpus file

Run `bddk-mcp build` with the owner's approval. A corpus file built before 2026-11-14 has no build fingerprint, so `build` rewrites every document from the seed (its sections and chunks are derived again; the vectors come from `seed_data/embeddings/`, nothing is embedded; the tokenizer must be available from the network or from `BDDK_EMBEDDING_MODEL_PATH`). `bddk-mcp info` says whether a file is current. No new file has to be built and swapped in by hand any more. A later change of the seed metadata, the section parser (including how section rows are derived for the index) or the chunking code is detected the same way and a plain `build` rewrites the file.

Two cases still need a fresh file. After a change of the embedding model or dimension, delete the corpus file and run `bddk-mcp build`; neither `build` nor `--force` switches an existing file to another model. After a change of the model revision, the passage prefix, the prefix separator or the vector dtype, `build` refuses and says to delete the file and run `bddk-mcp build --force`, because the seed embedding cache cannot see such a change. A document removed from the seed stays in an existing file; remove it by deleting the file and building again.

If a corpus file is replaced by hand, remove the old `<file>-wal` and `<file>-shm` as well: a non-empty `-wal` beside the replaced file is refused when the file is opened. The Docker image builds a fresh file and is not affected.

## What is not established

- A tagged or published 5.0.1 release.
- Independent human/legal approval of the corpus; a clean extraction is not that approval.
- Legal advice or authoritative proof of which rule applies to a real case.
- Measured live freshness for every corpus document.
- Bank-owned identity, CA, network, corpus-file distribution, backup, image-signing, promotion, and operational acceptance.
- Named client/model certification, approved expert judgments, or audit-grade product scores.
- Any model of legal currentness, amendment chains or cross-references; the assistant must verify those against the official source.
- Live acquisition against mevzuat.gov.tr. On 2026-11-12 the bulletin, monthly, trend, digest, announcement and institution tools and one `sync --force` of a BDDK-hosted decision ran against the live BDDK source from a sandbox (its DNS pre-check was stubbed in the trial script only, because that sandbox has no resolver). mevzuat.gov.tr did not answer from there (again on 2026-11-14), so the mevzuat-specific `sync` changes of both rounds (annex text, error-page fallthrough, charset decoding, wrapped table rows, catalog-field refresh) were tested with fixtures and fakes only, and the 47 canonical source URLs could not be opened. The LightOCR path was not exercised; the Docker image was not built locally; only the `image-smoke` CI job (success on `870a49a`) has built and exercised it.
- The displayed search relevance, its bands and the raw-cosine threshold default (0.80) are calibrated for `intfloat/multilingual-e5-base` on 101 queries with one model revision (see [Document Quality](DOCUMENT_QUALITY.md#displayed-search-relevance)); that is a calibration, not a retrieval evaluation, and any other embedding model gets an uncalibrated identity mapping with a 0.50 threshold. The unit tests use a fake embedder.
- Documents removed from the seed are not detected by `bddk-mcp build`; they stay in an existing file. Seed metadata, section parser and chunker changes are detected through the build fingerprint, but a change of the embedding settings is only refused, never repaired in place.
- Known gaps, listed in the 2026-11-14 changelog entry: the `kredi kartları` ranking (decision 758 before the 5464 sayılı Kanun), diacritic restoration for `ayni sermaye`, annexes of fifteen regulations, adopting decision or genelge numbers of Rehber and Genelge catalog entries, documents 909 and 917 (the same circular under two titles), the `£` for `≤` in `mevzuat_20029` EK-1 Tablo 1, a CPU-only torch for the serving image and a cached image build in CI.
- Retrieval beyond a few hundred thousand chunks: dense search is brute-force cosine over in-memory vectors, which is exact and fast at the current size; an ANN index (hnswlib or sqlite-vec) is the upgrade past that scale.
