Dense retrieval is exact cosine similarity over all chunk vectors held in memory; keyword and section search are FTS5 BM25 over Turkish-normalized text; dense and keyword candidates are merged with Reciprocal Rank Fusion, and the final order uses a heuristic relevance score. |

## What is ready at repository level

- Packaged stdio and Streamable HTTP MCP entry points with a strict public tool contract.
- Explicit corpus preparation: `bddk-mcp build`, `bddk-mcp sync`, `bddk-mcp export` (refuses a corpus file that is not ready and then writes nothing to `seed_data/`), and the read-only `bddk-mcp info`; the serving process never writes the corpus. A plain `sync` re-indexes a stored document that lacks current chunks from its stored text instead of downloading it again.
- Keeping the corpus current (since 2026-11-15, see [Deployment](DEPLOYMENT.md#keeping-the-corpus-current)): the read-only `bddk-mcp check-updates [--json]` lists new catalog entries, catalog entries no page lists and stored documents whose source changed, per page with the reason a page failed, and exits 0 (nothing), 3 (something to report) or 1 (error); `bddk-mcp sync --add ID` adds chosen entries from the live pages to the catalog and syncs only them. On 2026-11-15 against the 328-document seed it reported 16, 1336, 1340 and 1341 as new, 1350 as new on page 55, the three manual entries as not listed, and as changed only the eight BDDK documents whose seed `file_size` is the size of the patched text (their live sizes equal the sizes recorded at their sync); 248 BDDK and all 70 mevzuat sources were unchanged by its signals. Page 51 is parsed again (one table since 2026-11). The pdftotext backend stores text in the seed convention, and LightOCR decodes greedily.
- Fail-closed remote HTTP configuration (exact Host/Origin allowlists, JWT or explicit unauthenticated opt-in).
- Container image that carries the built corpus file, and a single-service Compose topology for local development; Railway remains a development/preview profile.
- Automated coverage across runtime, corpus build and readiness, retrieval, extraction quality and the HTTP transport.

## Upgrading an existing corpus file

Run `bddk-mcp build` with the owner's approval. A corpus file built before 2026-11-14 has no build fingerprint, so `build` rewrites every document from the seed (its sections and chunks are derived again; the vectors come from `seed_data/embeddings/`, nothing is embedded; the tokenizer must be available from the network or from `BDDK_EMBEDDING_MODEL_PATH`). `bddk-mcp info` says whether a file is current. No new file has to be built and swapped in by hand any more. A later change of the seed metadata, the section parser (including how section rows are derived for the index) or the chunking code is detected the same way and a plain `build` rewrites the file.

Two cases still need a fresh file. After a change of the embedding model or dimension, delete the corpus file and run `bddk-mcp build`; neither `build` nor `--force` switches an existing file to another model. After a change of the model revision, the passage prefix, the prefix separator or the vector dtype, `build` refuses and says to delete the file and run `bddk-mcp build --force`, because the seed embedding cache cannot see such a change. A document removed from the seed stays in an existing file; remove it by deleting the file and building again.

If a corpus file is replaced by hand, remove the old `<file>-wal` and `<file>-shm` as well: a non-empty `-wal` beside the replaced file is refused when the file is opened. The Docker image builds a fresh file and is not affected.

## What is not established

- A tagged or published 5.0.1 release.
- Independent human/legal approval of the corpus; a clean extraction is not that approval.
- Legal advice or authoritative proof of which rule applies to a real case.
- Measured live freshness for every corpus document. `check-updates` uses one cheap signal per source: a BDDK file of the same size, a mevzuat.gov.tr change without a dated amendment note (22 of the 70 stored mevzuat texts have none), catalog field changes of entries still listed and documents of other hosts are not seen; there is no stored fingerprint of each downloaded source (that would be a schema decision). `sync --refresh-catalog` still stops, now on the 5464 sayılı Kanun listed by pages 49 and 51 with different records; which page wins is not decided. A positive mevzuat change has not been observed live: on 2026-11-15 no official text carried a note the stored text lacked.
- Bank-owned identity, CA, network, corpus-file distribution, backup, image-signing, promotion, and operational acceptance.
- Named client/model certification, approved expert judgments, or audit-grade product scores.
- Any model of legal currentness, amendment chains or cross-references; the assistant must verify those against the official source.
- Live acquisition against mevzuat.gov.tr in `sync`. On 2026-11-15 mevzuat.gov.tr answered from the owner's machine to `check-updates`, which read the official text of all 70 stored mevzuat documents; no mevzuat document was synced. On 2026-11-12 the bulletin, monthly, trend, digest, announcement and institution tools and one `sync --force` of a BDDK-hosted decision ran against the live BDDK source from a sandbox (its DNS pre-check was stubbed in the trial script only, because that sandbox has no resolver). mevzuat.gov.tr did not answer from there (again on 2026-11-14), so the mevzuat-specific `sync` changes of both rounds (annex text, error-page fallthrough, charset decoding, wrapped table rows, catalog-field refresh) were tested with fixtures and fakes only, and the 47 canonical source URLs could not be opened. The LightOCR path was not exercised; the Docker image was not built locally; only the `image-smoke` CI job (success on `870a49a`) has built and exercised it.
- The displayed search relevance, its bands and the raw-cosine threshold default (0.80) are calibrated for `intfloat/multilingual-e5-base` on 101 queries with one model revision (see [Document Quality](DOCUMENT_QUALITY.md#displayed-search-relevance)); that is a calibration, not a retrieval evaluation, and any other embedding model gets an uncalibrated identity mapping with a 0.50 threshold. The unit tests use a fake embedder.
- Documents removed from the seed are not detected by `bddk-mcp build`; they stay in an existing file. Seed metadata, section parser and chunker changes are detected through the build fingerprint, but a change of the embedding settings is only refused, never repaired in place.
- Known gaps of the 2026-11-15 ranking change: the inflection-tolerant keyword pass of `search_document_store` does not run for the glossary expansion of a query, and a document that holds the query words only inflected still gets half the lexical boost (`_INFLECTED_LEXICAL_WEIGHT`, a calibration value), which now matters only for queries that name no document.
- Known gaps of the 2026-11-15 naming and section changes: a pasted sentence that quotes the whole title of another stored document lists that document first in `search_document_store` (9 of 534 sentence forms of the audit sweep moved one place down); an instrument name identifies a document only when every other word is a title word or its inflection, so "Bankaların Kredi İşlemlerine İlişkin Yönetmelik madde 12 üçüncü fıkra" (an ordinal fıkra is not parsed as a reference), abbreviations (SYR, İSEDES), one-word names whose word is in several titles of the type ("Özkaynak Yönetmeliği", "Bankalar Kanunu") and short names that several titles of the type hold without being the whole of one ("Sermaye Yeterliliği Yönetmeliği", "Finansal Tablolar Tebliği", "Kredi Riski Tebliği") scope nothing and name the candidates; a sentence that cites "5411 sayılı Kanun" lists the Kanun first (12 stored documents hold that short form; the audit sweep has no such sentence); definition, concept and jargon questions still miss the provision in 18 of 71 answerable audit questions on the section tool, and the semantic slots add one embedding to each unscoped section search.
- Known gaps, listed in the 2026-11-14 changelog entry: the `kredi kartları` ranking (decision 758 before the 5464 sayılı Kanun), diacritic restoration for `ayni sermaye`, annexes of fifteen regulations, adopting decision or genelge numbers of Rehber and Genelge catalog entries, documents 909 and 917 (the same circular under two titles), the `£` for `≤` in `mevzuat_20029` EK-1 Tablo 1, a CPU-only torch for the serving image and a cached image build in CI.
- Retrieval beyond a few hundred thousand chunks: dense search is brute-force cosine over in-memory vectors, which is exact and fast at the current size; an ANN index (hnswlib or sqlite-vec) is the upgrade past that scale.
